# Маршрутизация приложений и DNS: проверенная основа

Документ фиксирует только подтверждённые возможности официального AdGuard VPN CLI и ограничения, которые нужно проверить до реализации.

## Что подтверждено официальной документацией

### TUN

В режиме TUN AdGuard VPN создаёт виртуальный интерфейс и управляет системной маршрутизацией. В стандартном режиме AUTO туннель применяется системно; это не выбор отдельных приложений.

### Пользовательский режим маршрутизации SCRIPT

CLI поддерживает режимы туннельной маршрутизации NONE, AUTO и SCRIPT:

- NONE поднимает TUN, но не меняет таблицу маршрутизации.
- AUTO управляет системными маршрутами автоматически.
- SCRIPT запускает пользовательский скрипт при изменении состояния туннеля.

Команда включения режима: `adguardvpn-cli config set-tun-routing-mode SCRIPT`.

Команда создания шаблона с корректными правами: `adguardvpn-cli config create-route-script`.

В официальном Linux-примере первый аргумент скрипта — имя TUN-интерфейса (`INTERFACE="$1"`). Документация показывает добавление и удаление IP-маршрутов.

**Пока неизвестно и требует проверки на поддерживаемой версии CLI:** точная семантика вызовов при подключении, отключении, переподключении и ошибке; гарантии порядка вызовов; окружение и права; поведение, если скрипт завершился с ошибкой. Нельзя строить production-логику на предположении, что скрипт вызывается с одинаковыми аргументами для connect и disconnect.

### DNS через сам AdGuard VPN CLI

Официально документированы команды:

- `adguardvpn-cli config set-dns <server_address>` — задать DNS upstream;
- `adguardvpn-cli config set-change-system-dns on|off` — разрешить или запретить изменение системного DNS.

В режиме SOCKS эти параметры неактивны. В TUN CLI может управлять системным DNS. Это предпочтительный первый кандидат для DNS-интеграции оболочки, поскольку он не требует прямого редактирования пользовательских профилей NetworkManager.

**Неизвестно до проверки CLI на целевой версии:** как сбрасывается явно заданный DNS upstream к заводскому значению Default и можно ли безопасно прочитать/восстановить состояние «не задано». Поэтому нельзя подставлять слово `Default` в `set-dns` или обещать автоматическое восстановление без подтверждения.

## План безопасной реализации

1. Реализовать read-only разбор `adguardvpn-cli config show` с распознаванием DNS upstream, Change system DNS и Tunnel routing mode.
2. Сохранить исходные значения в пользовательском backup с правами 0600; проверять владельца, формат, версию и целостность данных.
3. Разрешить изменение DNS только после резервирования и проверки поддерживаемого способа восстановления исходного значения.
4. После каждого изменения перечитывать конфигурацию CLI и сравнивать с ожидаемым результатом.
5. Не изменять профили NetworkManager для основного DNS-сценария, пока не доказана необходимость.
6. Исследовать SCRIPT в изолированной тестовой среде: записать журнал вызовов скрипта при connect, disconnect, reconnect, потере сети и остановке CLI.
7. Только после подтверждения lifecycle-контракта проектировать транзакционное включение/выключение правил маршрутизации.
8. Для per-app routing отдельно проверить cgroup v2, nftables, fwmark и policy routing; предусмотреть IPv4, IPv6, DNS, локальные сети, rollback и восстановление после аварийного завершения.
9. Не показывать переключатели per-app routing до успешных интеграционных тестов.

## Важные ограничения

- SOCKS5 позволяет отдельному приложению использовать прокси только если само приложение умеет работать с SOCKS. Это не равнозначно прозрачной маршрутизации любого процесса.
- Исключения `site-exclusions` относятся к доменам/сайтам, а не к списку локальных приложений.
- Локальные unit-тесты не доказывают корректность реальной маршрутизации или отсутствие DNS/IPv6 утечек.
- Никакие реальные сетевые профили пользователя не должны попадать в публичный код, тесты или документацию.
