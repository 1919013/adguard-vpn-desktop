# Проектирование временной DNS-защиты для Debian

## Исходная проблема

В тестовой системе Debian 13 AdGuard VPN CLI сообщает, что системный DNS не удалось настроить. При этом CLI сохраняет upstream DNS в `~/.local/share/adguardvpn-cli/resolv.conf`, а системный `/etc/resolv.conf`, созданный NetworkManager, продолжает содержать DNS, полученный по DHCP. Для проверенного случая это означает, что системный резолвер и DNS CLI расходятся.

## Ограничения текущей версии 0.2.1

- `services/dns_manager.py` разрешает менять только два тестовых профиля и использует `nmcli connection modify`, то есть не предназначен для рабочих профилей.
- `services/dns_leak_guard.py` выполняет только read-only preflight по `/etc/resolv.conf` и маршрутам к DNS upstream.
- `services/network_manager.py` пока пустой модуль.
- Текущий Polkit action разрешает только операции split-tunnel.
- Существующий root helper не должен расширяться универсальными shell-командами или произвольными настройками NetworkManager.

## Выбранное направление исследования

Для временного применения DNS на активном устройстве NetworkManager документирует команду `nmcli device modify IFACE ...`: она изменяет текущие активные настройки устройства и не сохраняет изменения в connection profile. Это предпочтительнее постоянного `nmcli connection modify` для временного VPN-сеанса.

До включения функции в GUI необходимо подтвердить на поддерживаемой версии NetworkManager Debian 13:

1. Принимаются ли `ipv4.dns`, `ipv4.ignore-auto-dns`, `ipv6.dns` и `ipv6.ignore-auto-dns` для уже активных Ethernet и Wi-Fi устройств.
2. Как именно сбрасывать эти runtime-параметры к исходному состоянию DHCP/RA без переподключения и без записи в профиль.
3. Как NetworkManager формирует системный resolver, когда одновременно активны Ethernet и Wi-Fi.
4. Как ведут себя runtime-параметры при смене Wi-Fi, переподключении, DHCP renew, suspend/resume и перезапуске NetworkManager.
5. Как исключить локальные DNS stub resolvers и split-DNS сценарии, если upstream нельзя достоверно установить.

## Обязательная модель безопасности

- Не изменять постоянные NetworkManager connection profiles.
- Не использовать пользовательские имена профилей или интерфейсов, зашитые в исходный код.
- До изменения получить полный snapshot активных устройств и нужных IP-настроек.
- Snapshot хранить с проверкой владельца, типа файла, прав, версии и целостности.
- Проверять, что AdGuard VPN действительно подключён в TUN mode, а все используемые DNS upstream адреса получены из CLI resolver-файла и маршрутизируются через текущий TUN.
- Применять настройки транзакционно: если хотя бы одно устройство не прошло проверку, откатить все уже затронутые устройства.
- Повторно читать состояние после применения; не считать успешный exit code достаточной проверкой.
- При отключении VPN, смене TUN, завершении приложения и штатном закрытии восстанавливать исходные runtime-настройки.
- При аварийном завершении предусмотреть recovery action, которая может восстановить только объекты, принадлежащие приложению.
- Не удалять recovery state, пока восстановление всех устройств не подтверждено.
- Не обещать защиту от DNS/IPv6 утечек, пока не пройдены интеграционные тесты с реальными запросами.

## Предлагаемые этапы реализации

1. Read-only NetworkManager inventory и runtime snapshot.
2. Изолированный root helper с отдельным узким Polkit action только для apply/verify/restore DNS.
3. Unit-тесты в mock runner для validation, snapshot, partial failure, rollback, corrupted state и stale interface.
4. Интеграционные тесты на Debian 13 с активными Ethernet + Wi-Fi, затем отдельно с одним устройством.
5. Проверка DNS UDP/TCP и IPv6, включая route-to-upstream и фактический resolver path.
6. UI: состояние, dry-run, backup/recovery, применение и восстановление с явным подтверждением.
7. Автоматическое восстановление при disconnect и аварийном завершении.
8. Сборка .deb и проверка GitHub Actions до передачи пакета пользователю.

## Критерии готовности

Функция не считается готовой, если тесты проверяют только конфигурационные строки. Необходимо подтвердить реальные DNS-запросы через TUN, отсутствие запросов к DHCP DNS вне туннеля, корректную работу при двух активных физических интерфейсах и точное восстановление исходного состояния.
