# Проектирование временной DNS-защиты для Debian

## Исходная проблема

В тестовой системе Debian 13 AdGuard VPN CLI сообщает, что системный DNS не удалось настроить. При этом CLI сохраняет upstream DNS в `~/.local/share/adguardvpn-cli/resolv.conf`, а системный `/etc/resolv.conf`, созданный NetworkManager, продолжает содержать DNS, полученный по DHCP. Для проверенного случая это означает, что системный резолвер и DNS CLI расходятся.

## Ограничения текущей версии 0.2.1

- `services/dns_manager.py` разрешает менять только два тестовых профиля и использует `nmcli connection modify`, то есть не предназначен для рабочих профилей.
- `services/dns_leak_guard.py` выполняет только read-only preflight по `/etc/resolv.conf` и маршрутам к DNS upstream.
- `services/network_manager.py` пока пустой модуль.
- Текущий Polkit action разрешает только операции split-tunnel.
- Существующий root helper не должен расширяться универсальными shell-командами или произвольными настройками NetworkManager.

## Выбранное направление исследования

Для временного применения DNS на активном устройстве NetworkManager документирует команду `nmcli device modify IFACE ...`: она изменяет текущие активные настройки устройства и не сохраняет изменения в connection profile. Это предпочтительнее постоянного `nmcli connection modify` для временного VPN-сеанса.

До включения функции в GUI необходимо подтвердить на поддерживаемой версии NetworkManager Debian 13:

1. Принимаются ли `ipv4.dns`, `ipv4.ignore-auto-dns`, `ipv6.dns` и `ipv6.ignore-auto-dns` для уже активных Ethernet и Wi-Fi устройств.
2. Как именно сбрасывать эти runtime-параметры к исходному состоянию DHCP/RA без переподключения и без записи в профиль.
3. Как NetworkManager формирует системный resolver, когда одновременно активны Ethernet и Wi-Fi.
4. Как ведут себя runtime-параметры при смене Wi-Fi, переподключении, DHCP renew, suspend/resume и перезапуске NetworkManager.
5. Как исключить локальные DNS stub resolvers и split-DNS сценарии, если upstream нельзя достоверно установить.

## Обязательная модель безопасности

- Не изменять постоянные NetworkManager connection profiles.
- Не использовать пользовательские имена профилей или интерфейсов, зашитые в исходный код.
- До изменения получить полный snapshot активных устройств и нужных IP-настроек.
- Snapshot хранить с проверкой владельца, типа файла, прав, версии и целостности.
- Проверять, что AdGuard VPN действительно подключён в TUN mode, а все используемые DNS upstream адреса получены из CLI resolver-файла и маршрутизируются через текущий TUN.
- Применять настройки транзакционно: если хотя бы одно устройство не прошло проверку, откатить все уже затронутые устройства.
- Повторно читать состояние после применения; не считать успешный exit code достаточной проверкой.
- При отключении VPN, смене TUN, завершении приложения и штатном закрытии восстанавливать исходные runtime-настройки.
- При аварийном завершении предусмотреть recovery action, которая может восстановить только объекты, принадлежащие приложению.
- Не удалять recovery state, пока восстановление всех устройств не подтверждено.
- Не обещать защиту от DNS/IPv6 утечек, пока не пройдены интеграционные тесты с реальными запросами.

## Предлагаемые этапы реализации

1. Read-only NetworkManager inventory и runtime snapshot.
2. Изолированный root helper с отдельным узким Polkit action только для apply/verify/restore DNS.
3. Unit-тесты в mock runner для validation, snapshot, partial failure, rollback, corrupted state и stale interface.
4. Интеграционные тесты на Debian 13 с активными Ethernet + Wi-Fi, затем отдельно с одним устройством.
5. Проверка DNS UDP/TCP и IPv6, включая route-to-upstream и фактический resolver path.
6. UI: состояние, dry-run, backup/recovery, применение и восстановление с явным подтверждением.
7. Автоматическое восстановление при disconnect и аварийном завершении.
8. Сборка .deb и проверка GitHub Actions до передачи пакета пользователю.

## Критерии готовности

Функция не считается готовой, если тесты проверяют только конфигурационные строки. Необходимо подтвердить реальные DNS-запросы через TUN, отсутствие запросов к DHCP DNS вне туннеля, корректную работу при двух активных физических интерфейсах и точное восстановление исходного состояния.


## Требование к вкладке «Приложения» (согласованная спецификация)

Вкладка должна предлагать ровно два взаимоисключающих режима:

1. **Все приложения через AdGuard** — весь пользовательский трафик системы направляется через AdGuard VPN. В этом режиме интерфейс выбора отдельных приложений скрыт. Режим нельзя реализовывать как последовательный запуск приложений из каталога: требуется отдельный системный механизм маршрутизации всего трафика, согласованный с режимом маршрутизации AdGuard VPN CLI. До проверки механизма и возможности безопасного возврата в исходный режим пункт не должен заявляться как работающий.
2. **Избранные приложения через AdGuard** — только выбранные пользователем приложения направляются через VPN. Только в этом режиме показываются:
   - строка поиска с фильтрацией по началу названия без учёта регистра;
   - прокручиваемый список обнаруженных приложений с флажками;
   - добавление приложения по полному пути;
   - действия «Выбрать все», «Снять все», «Обновить список»;
   - сохранение пользовательского выбора;
   - управление запуском и прекращением VPN-маршрутизации приложения, когда backend подтверждает поддержку операции.

Переключение режима должно требовать явного подтверждения, если маршрутизация уже активна. Состояние выбора избранных приложений сохраняется при переключении на режим «Все приложения», но не применяется в нём. При возврате к режиму избранных прежний выбор восстанавливается.

Нельзя представлять текущий процессный launcher как режим «Все приложения»: сейчас `SplitTunnelRuntime` запускает один выбранный процесс в отдельной cgroup, проверяет TUN/DNS и удаляет свои правила по завершении. Это не системная маршрутизация всего трафика и не эквивалентно режиму «Все приложения через AdGuard».


## Текущее состояние реализации (2026-11-25)

- Добавлен read-only `NetworkManagerInventory`: динамически обнаруживает активные Ethernet/Wi-Fi устройства и их DNS IPv4/IPv6; имена интерфейсов и профилей не зашиты в код.
- `DNSLeakGuard` дополнен прямым UDP DNS-запросом к каждому upstream после проверки маршрута через TUN. Это подтверждает доступность upstream, но само по себе не доказывает, что все запросы системного resolver идут туда; для этого требуется отдельный интеграционный тест с наблюдением реального системного DNS-пути.
- Системное временное применение DNS, привилегированный DNS-helper, transactional restore и автоматическое аварийное восстановление пока не реализованы. Их нельзя считать закрытыми только на основании read-only inventory и upstream probe.
- Вкладка «Приложения» сохраняет режим `all`/ `selected` и скрывает каталог в режиме `all`. Автоматическое переключение CLI routing mode пока не подключено; UI явно сообщает об этом, поэтому режим не должен считаться активным только из-за выбора радиокнопки.


## Реализация 0.2.2 — промежуточный статус (2026-11-25)

### Уже добавлено в feature-ветку

- Отдельный services/dns_privileged.py и отдельный исполняемый файл adguard-vpn-desktop-dns-helper; DNS-действия имеют отдельный Polkit action и не расширяют интерфейс split-tunnel helper.
- Helper применяет только временные nmcli device modify настройки активных Ethernet/Wi-Fi устройств. Постоянные NetworkManager connection profiles не вызываются через nmcli connection modify.
- До изменения helper проверяет VPN TUN и маршрут к upstream с UID пользователя, от имени которого открыт GUI. Сохраняет boot ID, UUID каждого активного подключения, исходные и применяемые DNS-серверы и список устройств, к которым уже приступила транзакция.
- После изменения перечитывает фактические IP4.DNS/IP6.DNS. При ошибке откатывает уже затронутые устройства через nmcli device reapply; при незавершённом rollback не удаляет recovery state.
- Отдельная systemd-служба adguard-vpn-desktop-dns-guard следит за фазой транзакции, VPN и boot ID. Она запускается до первого изменения DNS, чтобы при аварийном завершении процесса обнаружить незавершённую фазу applying.
- Восстановление применяется только к тому же активному NetworkManager connection UUID. После reapply эффективные DNS-серверы сверяются с сохранённым исходным состоянием.
- DNS upstream теперь читаются из resolver-файла AdGuard VPN CLI; helper корректно разделяет IPv4 и IPv6 upstream.
- После применения GUI дополнительно проверяет системный resolver, маршрут к upstream и успешный UDP DNS-ответ. При провале GUI инициирует восстановление.
- services/routing_mode_manager.py переключает CLI на AUTO для всех приложений и SCRIPT для избранных. Перед переключением проверяет TUN и Change system DNS: on, после команды повторно читает конфигурацию и при неудачной проверке пытается вернуть предыдущий режим.
- Режим SCRIPT разрешён только при наличии обычного исполняемого setup_routes.sh; создание сценария запускается отдельным явным действием CLI и не перезаписывает существующий файл.
- Вкладка «Приложения» применяет режим только после подтверждения. Запуск избранных приложений блокируется, если CLI не находится в режиме SCRIPT. После смены режима интерфейс просит переподключить VPN.

### Что остаётся проверить до релиза

- Unit tests и сборка .deb в GitHub Actions должны завершиться успешно на последнем коммите.
- Необходима установка пакета и интеграционные испытания на Debian 13: активные Ethernet + Wi-Fi одновременно, один интерфейс, DHCP renew, смена сети, suspend/resume, отключение VPN, аварийное завершение GUI/helper, перезагрузка и проверка /etc/resolv.conf.
- nmcli device reapply и поведение временных device modify должны быть подтверждены на реальном NetworkManager пользователя. Unit tests используют mock runner и не доказывают реальное поведение ядра/NetworkManager.
- Для AUTO необходимо проверить реальную системную маршрутизацию после переподключения. Для SCRIPT — проверить работу созданного CLI route script, таблицы AdGuard VPN и cgroup/nftables правил для выбранных приложений.
- Проверка UDP upstream сама по себе не доказывает, что любой системный resolver, браузер, Flatpak или приложение не использует собственный DNS/DoH. Нужны интеграционные тесты с наблюдением реального трафика, включая IPv6.
- Только после этих проверок можно объявлять раздельную маршрутизацию и системную DNS-защиту готовыми на Debian 13.
